# BUG-004 결제 confirm이 클라이언트 amount를 order.price와 교차검증하지 않음

| 항목 | 값 |
|---|---|
| 심각도 | Major |
| 우선순위 | P2 |
| 상태 | Fixed (confirm 방어) / 결제 생성부 점검 잔여 |
| 관련 TC | TC-025 |
| 관련 POL | POL-040(에스크로 보관액) |
| 발견 위치 | `app/api/payments/toss/confirm/route.ts:8,49,57-68` |

## 환경
- master 브랜치 현재 코드, code-inspection.

## 재현 절차
1. matched(accepted) 의뢰의 화주 세션.
2. `confirm` 라우트에 `{ paymentKey, orderId, amount }` 전송 시 amount를 order.price보다 낮게 조작.

## 기대 결과
- POL-040: 에스크로 보관액 = 의뢰 확정금액. 서버가 `amount === order.price`를 검증하고 불일치 시 거절해야 함.

## 실제 결과
- confirm 라우트는 클라이언트 `amount`를 그대로 Toss 승인 및 escrow.total_amount/수수료 계산에 사용. **order.price와 대조하지 않음.**

## 원인 분석 (추정+확정)
- **확정**: confirm 코드에 order.price 대조 없음.
- **추정**: 실제 과소결제 성립 여부는 결제 생성부(`/shipper/orders/[id]/pay`)가 Toss 결제요청 금액을 서버에서 order.price로 고정했는지에 달림. Toss confirm은 "결제요청 시 등록된 금액"과 confirm amount 일치를 검증하므로, 생성부가 클라이언트 금액을 신뢰했다면 과소결제가 최종 성립. 생성부 검증 필요.

## 조치 (제안)
- confirm에서 order 조회 후 방어:
```ts
if (Number(amount) !== Number(order.price)) {
  return NextResponse.json({ error: "결제 금액 불일치" }, { status: 400 })
}
```
- 결제 생성부도 서버에서 order.price로 금액 고정하는지 확인·수정.
- 재검증: TC-025 재실행 + TC-020 정상결제 회귀.

## 조치 결과 (Fixed — confirm 방어선)
- `app/api/payments/toss/confirm/route.ts` escrow 분기에 `Number(amount) !== Number(order.price)` 시 400 반환 추가. tsc 통과.
- **잔여**: 결제 생성부(`/shipper/orders/[id]/pay`)가 Toss 결제요청 금액을 서버에서 order.price로 고정하는지 별도 점검 필요(다층 방어). 후속.

# 앱인토스 신원매핑 기반 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 앱인토스 토스로그인 사용자(userKey)를 기존 Supabase `users` 테이블에 shadow-auth 계정으로 매핑하는 백엔드 신원매핑 계층을 만든다.

**Architecture:** `users.id`가 `auth.users(id)`를 FK 참조하므로 토스 유저도 auth 계정이 필요하다. 토스 `userKey`마다 합성 이메일(`toss_<key>@apps.takca.internal`)로 shadow auth 유저를 1개 생성하고, `users.toss_user_key` 컬럼으로 매핑한다. 이렇게 하면 기존 RLS(`auth.uid()`)·FK·서버로직이 토스 유저에게도 그대로 적용된다(R4 해소). 이 계층은 앱인토스 콘솔 credential·결제정책(R1)과 무관하게 독립적으로 구현·테스트 가능하다.

**Tech Stack:** Next.js(App Router), TypeScript, Supabase(@supabase/supabase-js, service role), vitest(신규 테스트 러너).

**범위 밖(후속 계획):** 클라이언트 `appLogin()` 호출, authorizationCode→userKey 토큰 교환(콘솔 credential 필요), Supabase 세션 브리지, 결제/에스크로. 본 계획은 "userKey + 프로필이 주어졌을 때 users 레코드로 해소한다"는 순수 서버 로직까지만.

function fakeService(opts: {
  existing?: { id: string } | null
  createResult?: { user: { id: string } | null; error: { message: string } | null }
  upsertError?: { message: string } | null

    from: (_table: string) => ({
      select: () => ({
        eq: () => ({
          maybeSingle: async () => ({ data: opts.existing ?? null, error: null }),

      }),

        calls.upsert++
        return { error: opts.upsertError ?? null }
      },

    auth: {
      admin: {
        createUser: async (_args: unknown) => {
          calls.createUser++
          return opts.createResult ?? { user: { id: "new-uid" }, error: null }
        },
      },
    },
  }
  return { service, calls }

```ts
import type { SupabaseClient } from "@supabase/supabase-js"

const SHADOW_EMAIL_DOMAIN = "apps.takca.internal"

export interface TossProfile {
  name: string
  role: "shipper" | "driver"
}

export interface ResolvedUser {
  userId: string
  isNew: boolean
}

export function shadowEmail(tossUserKey: string): string {
  return `toss_${tossUserKey}@${SHADOW_EMAIL_DOMAIN}`
}

/**
 * 토스 userKey를 users 레코드로 해소한다.
 * 매핑이 없으면 shadow auth 유저(합성 이메일) 생성 후 users에 매핑.
 * service: service-role Supabase 클라이언트(auth.admin 권한 필요).
 */
export async function resolveUserByTossKey(
  service: SupabaseClient,
  tossUserKey: string,
  profile: TossProfile
): Promise<ResolvedUser> {
  const { data: existing } = await service
    .from("users")
    .select("id")
    .eq("toss_user_key", tossUserKey)
    .maybeSingle()

  if (existing) {
    return { userId: existing.id, isNew: false }
  }

  const email = shadowEmail(tossUserKey)
  const { data: created, error: createErr } = await service.auth.admin.createUser({
    email,
    email_confirm: true,
    user_metadata: { name: profile.name, role: profile.role, toss_user_key: tossUserKey },
  })
  if (createErr || !created?.user) {
    throw new Error(`shadow user 생성 실패: ${createErr?.message ?? "unknown"}`)
  }
  const userId = created.user.id

  const { error: upsertErr } = await service.from("users").upsert({
    id: userId,
    email,
    name: profile.name,
    role: profile.role,
    status: "active",
    toss_user_key: tossUserKey,
  })
  if (upsertErr) {
    throw new Error(`users 매핑 실패: ${upsertErr.message}`)
  }

  return { userId, isNew: true }
}
```

## 자체 검토 결과

- **스펙 커버리지:** 본 계획은 상위 스펙의 하위 PJ 3(토스로그인+신원매핑) 중 **백엔드 매핑 부분**만 담당. 클라 appLogin/토큰교환/세션브리지는 콘솔 credential 필요 → 후속 계획. 스펙 아키텍처(접근 A, toss_user_key)와 일치.
- **자리표시자:** 없음. 모든 단계에 실제 코드/명령/기대출력.
- **타입 일관성:** `resolveUserByTossKey(service, tossUserKey, profile)` 시그니처·`ResolvedUser`·`TossProfile`가 테스트와 구현에서 동일. `users` 컬럼(id/email/name/role/status/toss_user_key)은 001 스키마 + 017 마이그레이션과 일치.
- **의존성:** Task 0(vitest) → Task 2(테스트). Task 1(마이그레이션)은 독립이나 실제 DB 매핑엔 선행. 순서 0→1→2 권장.

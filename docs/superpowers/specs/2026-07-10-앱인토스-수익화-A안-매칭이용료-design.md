# 앱인토스 수익화 A안 — 기사 매칭 이용료 설계

날짜: 2026-07-10 · 범위: 앱인토스 미니앱(`apps-in-toss/`) + 백엔드(`app/api/apps-in-toss/*`) + 마이그레이션
선행: 마이페이지+매칭상세(2026-07-10 design) 위에 얹음

## 목적

앱인토스 초판은 결제를 빼고 "매칭까지만"으로 심의 통과(수익 0). 본 설계는 **2차 수익화** — 기사에게 **매칭 이용료(건당 정액)** 를 토스페이로 과금해 파트너 수익을 만든다. 탁송 대금(화주↔기사)은 계속 앱 밖 당사자 직접 → 에스크로/자금세탁 조항을 회피한 채 수익화한다.

## 확정 결정

- 과금 모델 = **건당 정액**(`MATCH_FEE_AMOUNT`, 기본 3,000원). 매칭 성사 시 기사에게 1회 부과.
- 게이팅 = **연락처 잠금해제형**. 결제해야 MatchDetail의 상대 연락처·채팅이 열림.
- 미결제 처리 = **24시간 후 매칭 자동취소** → 주문 다시 pending → 화주가 다른 입찰 수락 가능.
- 결제 수단 = **토스페이 단건**. (⚠️ 심사자가 "연락처 잠금해제 = 디지털 권한 = 인앱결제(IAP)"로 볼 여지 → 토스 채널톡 사전확정. 설계는 토스페이 전제, 확정 결과 따라 IAP로 스왑 가능하게 결제 어댑터 경계 분리.)
- 부과 대상 = **기사만**. 화주는 무료.

## 데이터 모델 — 마이그레이션 019

```
match_fees (
  id            uuid pk,
  match_id      uuid not null references matches(id) on delete cascade,  -- UNIQUE
  driver_id     uuid not null references users(id),
  amount        integer not null,          -- 부과 시점 금액 스냅샷
  status        text not null default 'pending'
                check (status in ('pending','paid','refunded','cancelled')),
  toss_payment_key text,                    -- 토스페이 승인 결과 키(또는 IAP orderId)
  paid_at       timestamptz,
  expires_at    timestamptz not null,       -- created_at + 24h
  created_at    timestamptz not null default now(),
  unique(match_id)
)
```
- RLS: select/update = 해당 기사(driver_id=auth.uid()) 또는 매칭 화주(order.shipper_id). **018 헬퍼(`is_shipper_of_order`) 재사용**해 재귀 회피.
- insert는 서버(service-role)만 — 화주 입찰수락 오케스트레이터가 생성.

## 컴포넌트 / 흐름

### 1. 매칭 생성 시 fee 생성 (백엔드)
- 기존 `approveBidFlow`(app/api/apps-in-toss/bids/approve) 확장: match 생성 직후 `match_fees` insert(status=pending, amount=MATCH_FEE_AMOUNT, expires_at=now+24h). 멱등(UNIQUE match_id, on conflict do nothing).

### 2. 결제 (토스페이 단건, 어댑터 경계)
- `POST /api/apps-in-toss/match-fee/create` (Bearer): match_fee 조회·검증(기사 본인·pending·미만료) → 토스페이 결제생성 API로 `payToken` 발급 반환.
- SDK: 미니앱에서 결제창 호출(요청은 payToken 기반).
- `POST /api/apps-in-toss/match-fee/confirm` (Bearer): payToken 승인 → match_fees status=paid, toss_payment_key, paid_at 기록. 멱등.
- 결제 로직은 주입형 오케스트레이터 + DI fetch로 TDD(기존 loginFlow 패턴). 토스페이 호출부는 `lib/apps-in-toss/matchFee.ts`로 격리 → IAP 전환 시 이 파일만 교체.

### 3. MatchDetail 게이팅 (프론트)
- 진입 시 match_fee status 조회.
- 기사 뷰: `paid` → 연락처·채팅 오픈 / `pending` → 잠금 + "매칭 이용료 N원 결제하고 연락처 받기" CTA(만료 카운트다운) / `cancelled` → "매칭이 취소되었어요".
- 화주 뷰: `paid` → 기사 연락처 오픈 / `pending` → "기사 확정 대기중"(무료).

### 4. 24h 자동취소
- **Lazy 체크**(주 경로): MatchDetail·MyOrders·DriverMy·Feed 조회 시, 만료+pending fee 발견하면 백엔드 `POST /api/apps-in-toss/match-fee/expire`(또는 조회 라우트 내 정리) 호출 → match cancelled, order status→pending, bid 재입찰 가능 상태, match_fee cancelled. 원자적 처리(RPC 또는 서버 트랜잭션).
- **크론**(보조): 기존 Vercel 크론에 만료 스윕 추가(Hobby 일1회). lazy가 주, 크론이 백스톱.

## 심의 / 법무

- 토스페이 = 실물/서비스 결제 대상(문서 명시). 매칭 이용료 = 중개 서비스 대가 → 정당.
- 탁송 대금은 앱 밖 당사자 직접 → 미니앱은 대금 보관·정산 안 함 → 자금세탁(정책 1-2)·PG(6-2) 회피 유지.
- 약관: "매칭 이용료(회사가 기사에게 부과하는 중개 서비스 이용료, 건당 N원)" 조항 + 환불정책(결제 후 연락처 열람 전 취소 시 환불 기준) 추가 → `More.tsx` 이용약관/신규 섹션 반영.
- ⚠️ 결제수단 분류(토스페이 vs IAP)는 토스 채널톡 확정 후 확정.

## 의존성 (live 실행 전제)

- 토스페이 **가맹점 키**(앱인토스에서 별도 발급) + mTLS 인증서 + 앱 정보 심사 승인. login live(R6~R8)와 동일 게이트.
- 승인 전: DB·라우트·게이팅·자동취소 로직·단위테스트까지 완성. 결제 실행 연결만 승인 후.

## 범위 밖 (후속)

- 정기결제/구독, 무료 크레딧, 매칭액 % 모델, 화주 과금, 세금계산서.
- 초판 심의는 "매칭까지만(수익0)" 그대로. A안은 결제 얹은 2차 버전으로 별도 검토요청.

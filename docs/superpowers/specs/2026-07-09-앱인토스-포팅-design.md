# 탁카 앱인토스 포팅 설계 (Apps in Toss Port)

- 작성일: 2026-07-09
- 상태: 승인됨 (브레인스토밍 완료)
- 대상: 탁카(차량 탁송 중개) 앱인토스 미니앱 버전

## 1. 배경 / 목표

기존 독립 웹앱 `takca.vercel.app`(Next.js + Supabase, 자체 지갑·에스크로·자체 인증·자체 광고)은 **그대로 유지·운영**한다. 이와 별개로 토스 슈퍼앱(3,000만 유저) 유통망 진입을 위해 **앱인토스 전용 미니앱 버전**을 신규 제작한다.

앱인토스는 자체 지갑·에스크로·외부 로그인·외부 광고를 제약하므로, 인증·결제·광고 3축을 앱인토스 규격으로 재설계한다. 비즈니스 로직과 데이터(주문/입찰/매칭/컨디션리포트)는 최대한 재사용한다.

### 채널 전략 (확정)
- **둘 다 유지 (듀얼 채널)**: 독립 웹앱 + 앱인토스 미니앱 동시 존재.
- 공유: 백엔드(Supabase DB + 비즈니스 로직). 분기: 프론트 + 인증 + 결제 + 광고.

### 첫 버전 범위 (확정)
- **핵심 플로우만**: 화주 주문등록 → 기사 입찰/수락 → 매칭 → 토스페이먼츠 에스크로 결제 → 탁송완료 → 구매확인 → 에스크로 해제(정산).
- 커뮤니티·자체광고·상세통계·리뷰 등은 후속.

## 2. 아키텍처 (접근 A: 백엔드 공유 + 신원 매핑)

- 기존 Supabase 프로젝트 `ypqwifcbgemmaatnzcbb`를 **그대로 재사용**한다. orders / bids / matches / condition_report 등 스키마·서버 로직 공유.
- 앱인토스는 **토스 로그인만** 허용 → 토스가 발급하는 사용자 식별자(userKey)를 기존 `users` 테이블에 **`toss_user_key` 컬럼(신규, UNIQUE, nullable)** 으로 매핑한다.
- 한 사용자가 웹(Supabase auth) / 앱인토스(토스로그인) 어느 채널로 들어와도 동일한 `users` 레코드에 연결될 수 있게 매핑 계층을 둔다. (동일인 병합은 후속 — MVP는 채널별 독립 계정 허용)
- 두 채널이 같은 주문 데이터를 보므로, 화주는 웹·기사는 앱인토스 같은 혼용 거래가 가능하다.

### 데이터 흐름
```
앱인토스 미니앱(WebView)
  └ 토스로그인 → toss_user_key
     └ 신원매핑 계층 → users 레코드(row)
        └ 기존 서버 액션/RLS → orders/bids/matches/escrow(토스페이먼츠)
```

### 신원/인가
- 서버는 요청의 토스 세션을 검증 → `toss_user_key`로 `users` 조회 → 해당 user 컨텍스트로 기존 로직 실행.
- 기존 RLS는 Supabase `auth.uid()` 기반이므로, 앱인토스 경로는 서버 액션에서 서비스 롤 + 명시적 소유검증으로 처리하거나, 토스 유저를 위한 세션 브리지를 둔다. (상세는 하위PJ 3 계획에서 확정)

## 3. MVP 핵심 플로우

```
[화주] 주문등록
  → [기사] 피드 입찰/수락 → 매칭 생성
  → 토스페이먼츠 에스크로 결제(화주 결제→예치)
  → 탁송완료 리포트
  → 화주 구매확인
  → 에스크로 해제(기사 정산)
```

### 결제 / 에스크로
- 탁송 = 실물성 용역 → 앱인토스 **인앱결제(디지털/앱마켓 경유)** 대상 아님 → **토스페이먼츠 PG의 에스크로**(카드·가상계좌·계좌이체, 결제→배송등록→구매확인) 사용.
- 기존 자체 지갑·에스크로 로직은 **앱인토스 경로에서 미사용**. 독립 웹앱은 기존 방식 유지.
- ⚠️ **미해결/검증 필요**: 앱인토스 미니앱 WebView 내부에서 외부 PG(토스페이먼츠) 결제창 호출이 정책상 허용인지 문서가 상충(guide.html은 "실물=토스페이"만 명시, 블로그·PG문서는 실물=PG연동 권장). **앱인토스 콘솔 등록 + 사업자 업종 심사 후 토스에 직접 확인**하여 확정한다. 만약 불가 시 대체안: 앱인토스 인앱결제로 예치 후 자체 정산(정책·수수료 재검토).

### 인증
- 토스 로그인 → `users.toss_user_key` 매핑. 최초 로그인 시 역할(화주/기사) 온보딩.

### KYC + AI 고지
- 기사 온보딩에 KYC 유지(운송 안전). Anthropic 기반 서류 AI 분석 유지.
- 앱인토스 정책: 생성형 AI 결과물은 **"AI 결과물" 명시 고지** 의무 → KYC 분석 결과 화면에 배지/문구.

### 광고
- 앱인토스 경로에서는 자체 `AdBanner` 렌더링 금지(외부 광고 네트워크 불가 정책). 앱인토스 광고 SDK 연동은 후속.

## 4. 하위 프로젝트 분해 및 순서

각 하위 프로젝트는 자체 스펙 → 계획 → 구현 사이클을 가진다. 본 문서는 상위 설계이며, 실제 구현은 하위 PJ별로 진행한다.

| # | 하위 프로젝트 | 코드 | 선후 관계 |
|---|---|---|---|
| 1 | 앱인토스 콘솔 등록 + 사업자 서류 심사 제출 | 비코드(사용자) | 지금 병행 (심사 1~2영업일) |
| 2 | 미니앱 스캐폴딩 (앱인토스 SDK / WebView 프레임) | O | 1 심사 중 착수 가능 |
| 3 | 토스로그인 + 신원매핑 (`toss_user_key`) | O | 2 이후 |
| 4 | 핵심 플로우 화면 (주문→입찰→매칭), DB 재사용 | O | 3 이후 |
| 5 | 토스페이먼츠 에스크로 결제 연동 | O | 4 이후 + 결제수단 정책 확정 후 |
| 6 | KYC + AI 고지 | O | 병행 가능 |

MVP 정의 = 하위 PJ **2~5** (핵심 플로우 + 결제). 하위 PJ 6은 기사 진입이 필요한 시점에.

## 5. 선행 조건 / 사용자 액션

- [x] 사업자 등록 완료 (사업자번호 발급됨)
- [ ] 앱인토스 콘솔 앱 등록 + 사업자 서류 제출 (사용자, 심사 1~2일)
- [ ] 결제 정책 확정: 앱인토스 내 토스페이먼츠 에스크로 사용 가능 여부 토스 확인
- [ ] 화물자동차운수사업법상 **운송주선사업 허가** 필요 여부 법률 검토 (규제 리스크, 별도 트랙)
- [ ] 사업자등록증 **업종**이 앱인토스 서비스 업종과 일치하는지 확인 (불일치 시 출시 제한)

## 6. 리스크 / 미해결

- **R1 (결제 정책)**: 앱인토스 내 외부 PG(토스페이먼츠) 에스크로 허용 여부 미확정. → 콘솔 등록 후 토스 문의로 확정. 불가 시 결제 설계 변경.
- **R2 (규제)**: 탁송 중개가 화물운송주선사업 허가 대상일 수 있음. 미인가 운영 리스크. → 법률 검토.
- **R3 (업종 일치)**: 사업자 업종 ≠ 미니앱 서비스 업종이면 출시 반려. → 업종 확인.
- **R4 (신원/RLS)**: 토스로그인 유저를 기존 Supabase RLS(`auth.uid()`)에 어떻게 태우는지 상세 미확정. → 하위 PJ 3 계획에서 확정.
- **R5 (VAT 면세)**: 면세사업자는 앱인토스 등록 불가. → 과세사업자 확인.

## 6-B. 아키텍처 정정 (2026-07-09, SDK 문서 정독 후)

당초 "미니앱 프론트를 Next 라우트그룹(`app/(apps-in-toss)/`)에 둔다"는 가정은 **폐기**한다. 앱인토스 `@apps-in-toss/web-framework`는 **Vite 기반 SPA 번들**을 생성해 콘솔에 업로드 → 토스 CDN이 호스팅하는 구조다. Next.js 서버렌더/서버액션은 토스 WebView 번들 안에서 실행되지 않는다.

**확정 아키텍처 A′ (모노레포):**
- **미니앱 프론트** = 같은 git 레포 내 별도 서브폴더 `apps-in-toss/` 의 **Vite + React SPA**(자체 package.json, 루트 Next와 의존성/스크립트 분리). 빌드 산출물 `dist` → 콘솔 업로드.
- **백엔드** = 기존 Next.js(Vercel) API 라우트/route handler를 **HTTPS로 호출**해 공유. 토스 토큰교환·mTLS·에스크로도 여기.
- 신원매핑(`resolveUserByTossKey`, 017)·비즈니스 로직·Supabase는 그대로 재사용.

**확정 SDK 사실:**
- 셋업: `npm i @apps-in-toss/web-framework` + `npx ait init` → `granite.config.ts`
- `granite.config.ts`: `appName`, `brand{displayName, primaryColor:'#F97316', icon(콘솔 URL)}`, `web{host, port, commands:{dev:'vite dev', build:'vite build'}}`, `permissions`, `outdir:'dist'`
- 로그인: 클라 `appLogin()`(from `@apps-in-toss/web-framework`) → `{authorizationCode, referrer}`(코드 10분·일회성; referrer DEFAULT/SANDBOX)
- 서버 교환: POST `/api-partner/v1/apps-in-toss/user/oauth2/generate-token` `{authorizationCode, referrer}` → `{accessToken, refreshToken, expiresIn}`; GET `/api-partner/v1/apps-in-toss/user/oauth2/login-me` (Bearer) → `{userKey, name, phone, birthday, ci, ...}`(암호화). 스코프: user_ci/user_name/user_phone 등
- 세션 브리지: 교환된 userKey → `resolveUserByTossKey` → 해당 shadow-auth 유저의 Supabase 세션 발급 → 기존 RLS 작동

**신규/갱신 리스크:**
- **R6 (mTLS)**: 파트너 API 호출에 mTLS 클라이언트 인증서 필수. 발급 경로·Vercel 서버리스 아웃바운드 mTLS 가능 여부 미확정. → #3 런타임 선행조건.
- **R7 (API 호스트)**: `/api-partner/...` 베이스 URL 미확인. → 콘솔/문서 확인.
- **R8 (credential)**: client_id/secret 미수령. → #3 실행 직전 필요(코드는 env 주입형으로 선작성).

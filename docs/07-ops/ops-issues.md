# 탁카 운영 이슈 시나리오 (Stage 7)

실제 시스템 구조에서 발생 가능한, 서로 다른 3범주 이슈. 각 이슈는 탐지 → 영향평가 → 즉시대응 → RCA(근본원인, 5 Whys) → 복구 → 재발방지 타임라인.

> **공통 전제 — 탐지 공백**: 현재 코드에 에러 트래킹·결제 정합성 모니터·비용 알림이 **없음**(결제 confirm 라우트는 try/catch로 500만 반환, 로그/알림 없음). "탐지 수단 부재" 자체가 개선계획 최우선.

## OPS-001 [범주 A · 기술장애] 결제 승인–에스크로 기록 부분실패 (돈만 빠지고 미기록)

**시스템 근거**: `app/api/payments/toss/confirm/route.ts` — Toss 승인 API 호출(L43) → 성공 후 `escrow.insert`(L59) → `orders/matches update`(L69-70)가 **하나의 트랜잭션이 아님**. Toss는 실제 카드 청구가 완료됐는데, 직후 escrow insert가 실패(DB 순단·타임아웃·제약위반)하면 **화주는 결제됐으나 시스템엔 escrow 없음**.

### 탐지
- **실제 탐지 수단 없음.** 화주 CS 문의("결제했는데 진행이 안 돼요")로 뒤늦게 인지. 카드사 청구와 escrow 부재 대사(reconciliation) 배치 없음.

### 영향평가
- 범위: Toss 승인 성공 & 후속 insert 실패한 모든 건. 저빈도이나 **건당 실자금** 문제 → 심각도 **High**.
- 2차 영향: 화주 신뢰 붕괴, 환불 수작업, 기사 매칭 상태 불일치(order in_progress 안 됨).

### 즉시대응
1. Toss 대시보드 승인내역 ↔ `escrow.pg_transaction_id` 대사로 누락 건 식별.
2. 누락 건: escrow 수동 생성(멱등성 — `pg_transaction_id` 기준 재확인) 또는 화주에게 전액 환불(POL-043).
3. 화주 개별 공지.

### RCA (5 Whys)
1. 왜 돈만 빠졌나 → Toss 승인 후 escrow insert 실패. 2. 왜 복구 안 됐나 → 승인+기록이 원자적이 아니고 보상 로직 없음. 3. 왜 몰랐나 → 대사·에러 알림 부재. 4. 왜 알림이 없나 → 관측성 미구현. 5. 근본 → **결제 정합성을 코드 흐름의 성공에만 의존, 이중기록/대사 안전망 없음**.

### 복구
- 대사 스크립트로 과거 누락 소급 정정. 영향 화주 환불/진행 택1.

### 재발방지 (구조적)
- confirm 실패 시 **에러 트래킹 알림**(Sentry 등) + 실패 로그에 paymentKey 기록.
- **일 1회 대사 크론**: Toss 승인내역 ↔ escrow 누락 자동 검출·알림.
- escrow insert 실패 시 자동 보상(재시도 큐 또는 즉시 Toss 취소).
- 관련: BUG-011(미결제/기처리 구분)과 함께 상태 메시지 정확화.

## OPS-002 [범주 B · 데이터/개인정보] 위치정보(GPS) 무동의 수집 지적

**시스템 근거**: `driver_locations`(migration 006) — 기사 실시간 GPS를 저장·화주에게 실시간 노출하나, **개인위치정보 별도 동의 UI·보관/파기 정책 부재**(POL-081, RISK-003). 위치정보의 보호 등에 관한 법률상 개인위치정보는 별도 동의 필수.

### 탐지
- 이용자 문의("내 위치가 왜 계속 보이나요") 또는 개인정보위/신고. 내부 자동 탐지 없음.

### 영향평가
- 범위: 실시간 추적을 사용한 모든 기사. **법적 리스크(과태료·시정명령)** + 신뢰 훼손 → 심각도 **High(법규)**.
- 데이터: 완료 거래 이후에도 위치 이력이 파기 없이 잔존 가능(보관정책 없음).

### 즉시대응
1. 위치 수집을 **진행 중 거래로 한정**하도록 서버측 게이트(매칭 in_progress 아닌 경우 위치 API 거부).
2. 동의받지 않은 위치 이력 파기, 수집 목적·기간 고지.
3. 별도 동의 UI 긴급 배포 전까지 실시간 추적 기능 일시 비활성 검토.

### RCA (5 Whys)
1. 왜 지적됐나 → 무동의 개인위치정보 수집. 2. 왜 동의 없이 수집 → 별도 동의 플로우 미구현. 3. 왜 미구현 → 기획 시 위치정보법 요건 누락(정책서 소급에서야 식별). 4. 왜 잔존하나 → 파기 배치·보관기간 미정. 5. 근본 → **규제 도메인 요건을 기능 구현이 선행하고 컴플라이언스가 후행**.

### 복구
- 동의 UI 배포 후 재동의 획득, 미동의자 위치기능 차단. 이력 파기 배치 도입.

### 재발방지 (구조적)
- 위치 수집 지점에 **동의 여부 서버검증** 강제(동의 레코드 없으면 저장 거부).
- 거래 완료 트리거로 위치 이력 자동 파기 + 보관기간(예: 분쟁대비 N일) 정책 확정(POL-081).
- 개인정보 수집항목 표(POL-080) 기준 정기 점검 체크리스트.

## OPS-003 [범주 C · 악용] KYC 재제출 무제한 악용 — Vision 비용폭증 + 임계값 gaming

**시스템 근거**: `app/api/kyc/verify/route.ts` — 거절(rejected) 후 **재제출 횟수·쿨다운 제한 없음**(BUG-009, POL-052). 매 제출마다 Storage 업로드 + Claude Vision 실행. confidence ≥0.72 자동승인 임계값이 고정.

### 탐지
- Anthropic 사용량/비용 급증. 특정 user_id의 kyc_submissions 다발 로우. **비용 알림 없음** → 월 청구서에서 사후 인지 가능.

### 영향평가
- 범위: 악의적 기사 1인만으로도 API 비용 급증. 위·변조 서류를 조금씩 바꿔 반복 제출 시 임계값 통과 확률 상승 → **미검증 기사 진입(안전·신뢰 직결)** → 심각도 **Medium~High**.

### 즉시대응
1. 해당 user_id KYC 제출 차단, 이미 승인됐다면 verification_status 회수(→ pending/rejected)하고 거래 정지.
2. Anthropic 사용량 급증 계정 격리.

### RCA (5 Whys)
1. 왜 비용폭증/우회 → 무제한 재제출. 2. 왜 무제한 → rate limit·쿨다운 미구현. 3. 왜 우회 가능 → 자동승인 임계값 고정 + 반복 시도 억제 없음. 4. 왜 못 막았나 → 제출 남용 탐지·비용 알림 없음. 5. 근본 → **비용·자격판정을 외부 AI 단발 호출에 의존, 남용 방지 계층 부재**.

### 복구
- 우회 승인 계정 전수 재심사(수동). 재제출 이력 다발 계정 플래그.

### 재발방지 (구조적)
- 제출 진입부 **재시도 제한**(예: 24h N회 초과 시 쿨다운/수동검토 전환) — POL-052 확정.
- 반복 거절 계정은 자동승인 임계값 우회 불가 → **누적 실패 시 무조건 manual_review**.
- Anthropic **비용/사용량 알림** 임계 설정.
- 관련: BUG-008(파일 검증)으로 비정상 업로드 선차단.

## 이슈 → 개선 항목 연결
각 OPS 재발방지 항목은 `improvement-plan.md`로 통합·우선순위화한다. 3개 이슈 공통으로 **탐지/관측성 부재**가 드러났으며 이것이 개선 1순위다.
